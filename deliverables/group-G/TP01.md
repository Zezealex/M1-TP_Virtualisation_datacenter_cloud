## Questions obligatoires

**Q1 — `hostname` vs `hostname -f`**
`hostname` lit le nom court positionné localement (`/etc/hostname`, exposé via `/proc/sys/kernel/hostname`) — aucune résolution effectuée. `hostname -f` fait un appel de résolution de nom (getaddrinfo avec canonicalisation) pour retourner le FQDN complet, en s'appuyant sur `/etc/hosts` ou le DNS.

**Q2 — Pourquoi `/etc/hosts` est important dans un cluster Proxmox**
Corosync (heartbeat/quorum), les certificats TLS auto-générés (SAN sur le FQDN) et `pvecm add` dépendent tous d'une résolution de nom fiable entre les nœuds. Dans un LAB sans DNS interne dédié, `/etc/hosts` est la seule source de résolution : une entrée incohérente ou absente casse silencieusement ces mécanismes plus tard, souvent au pire moment (ajout d'un nœud au cluster).

**Q3 — `default via ...` dans `ip route`**
C'est la route par défaut : la règle appliquée à tout paquet dont l'adresse de destination ne correspond à aucune route plus spécifique dans la table. `default via X dev Y` = tout trafic sans meilleure route part vers la passerelle `X` par l'interface `Y`.

**Q4 — `vmx` / `svm` dans `/proc/cpuinfo`**
Flags indiquant le support matériel de la virtualisation assistée par le CPU : `vmx` pour Intel VT-x, `svm` pour AMD-V. Leur présence (ici exposée par VMware au CPU virtuel du guest) est le prérequis pour que KVM fonctionne avec accélération matérielle plutôt qu'en émulation logicielle pure.

**Q5 — Rôle de `pveproxy`, `pvedaemon`, `pvestatd`, `pve-cluster`**
- `pveproxy` : proxy HTTPS qui expose l'API REST et l'interface web sur le port 8006.
- `pvedaemon` : exécute les opérations privilégiées demandées via l'API, avec vérification des permissions.
- `pvestatd` : collecte périodiquement l'état des ressources (VM, stockage, réseau) pour le monitoring/l'affichage.
- `pve-cluster` : fait tourner `pmxcfs`, le système de fichiers de configuration répliqué monté sur `/etc/pve` — actif dès l'installation, même en standalone.

**Q6 — Pourquoi `apt-get update failed: exit code 100` ne suffit pas**
Le code 100 est générique à toute erreur APT (dépôt inaccessible, clé GPG invalide, 401, dépôt malformé...) — il ne dit ni la cause ni le dépôt en cause. Il faut relire la sortie complète de `apt update` dans le terminal (pas le message tronqué de l'UI Proxmox) pour identifier la ligne d'erreur précise, comme le `401 Unauthorized` sur `enterprise.proxmox.com` trouvé ici.

## Ce que nous avons compris

- `vmbr0` porte la route par défaut vers Internet (NAT), et non le réseau LAB — cohérent puisque le réseau LAB n'existe pas encore à ce stade du parcours.
- `/etc/pve` n'est pas un répertoire disque classique : c'est un montage FUSE (`pmxcfs`, service `pve-cluster`) qui présente une base de configuration répliquée comme un système de fichiers, avec des dates/tailles atypiques (`Jan 1 1970`, tailles à 0) qui trahissent ce fonctionnement.
- La virtualisation imbriquée (Proxmox dans VMware) doit être validée à deux niveaux : côté hyperviseur hôte (case VT-x/EPT dans VMware) **et** côté invité (flag CPU + module `kvm_intel` réellement chargé) — les deux ont été vérifiés.
- Un nœud Proxmox standalone fait déjà tourner `pve-cluster`/`pmxcfs` avant toute création de cluster : le nom du service est trompeur.
- Les dépôts Enterprise Proxmox/Ceph nécessitent une souscription payante ; en lab, on utilise systématiquement les dépôts `no-subscription`.
